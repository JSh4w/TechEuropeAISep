5. Your four-phase plan against what exists

Your plan

  1. Pull all data for the location into classes. done location.collate
  2. Deterministic possibility checks. done possibility.hard, 12 checks
  3. Agentic possibility checks: is it hard-denied by policy? done possibility.policy, live on Gemini; quotes unverifiable because councils block downloads, confidence held at 0.6
  4. Suitability, deterministic and agentic in parallel:
    cable cost by distance exists in finance/cost.py
    approval likelihood missing and a stated non-goal in the planning spec
    best-spot siting agent missing, in no spec; inputs (slope grid, flood and designation polygons, lines) are all in LocationData; homes would be judged by an agent looking at the map
    local sentiment exists in suitability/, wired into the run

How the pipeline orders things instead

  1. location → capacity → title → human confirms size and position
  2. then grid, site_land, market, sentiment in parallel; then financial and planning; then synthesis

The difference that matters: the pipeline decides battery size from grid capacity first and asks the human before any land check runs. Your plan checks the land first. Both are defensible; they need reconciling, because a site that is 94% Flood Zone 3 (Bridgwater) currently reaches the human confirmation step looking fine.

Cheapest reconciliation: run collate and the hard checks beside capacity, and show blockers and caveats in the confirmation prompt. The human then confirms with the land facts in view, and blocked sites can stop early the same way out_of_area does today.

  1. Agree with Josh: one collate activity after location, LocationData as an optional field on NodeInput. Everything else hangs off this.
  2. Connectors 1, 3 and 9 (title, site_land, map parcels): about an hour, replaces two placeholders with real data and puts the real title boundary on the map. No model needed.
  3. Connector 7 (verdict sees blockers): without it the report can say "go" on a site the hard checks rule out.
  4. Connectors 6 and 8 (policy agent into planning, real place names into sentiment): a second visible agent, and better search results from the first.
  5. Connector 2 (capacity outside UKPN): decides whether the demo can use sites outside London, the South East and East Anglia.
  6. Move the HTTP bridge out of src/bessible/api/ (say to bessible/http/) or rename ours, so bessible.api means one thing.
  7. Then the siting agent, now that there is a real map to show its suggestion on.
