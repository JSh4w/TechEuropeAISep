Bessible: data sources

What each external API in src/bessible/api/ gives us, and whether we use it to answer “is it possible, and if so feasible, to build a BESS here?”  ·  state as of 19 Sep 2026

USED feeds the assessment PARTLY useful but needs a change first NOT USED modelled (responses must parse) but ignored

Every module in api/ has the same four sections: 1. Request, 2. Response, 3. Response sub-models, 4. Not from the API (request builders, registries, transforms). Sections 1–3 model the wire format only; api/__init__.py summarises each source.

Every response model has extra="forbid", so all fields an API returns are modelled even when we ignore them: an unknown field means our model is stale. “Not used” therefore means “parsed, then ignored”, not “missing”.

1. The flow

1. Locatepostcode or lat/lon → coordinate, human-readable addresspostcodes_io · nominatim
→
2. The sitetitle boundary polygon containing the point: the thing we assessplanning_data
→
3. Land & constraintsdesignations, land grade, flood zone, habitats on / near the polygonplanning_data · natural_england · ea_flood
→
4. Terrain1 m heights and slope inside the polygonea_lidar · open_meteo (fallback)
→
5. Gridnearest substation, headroom, queue, linesukpn · nged · ssen_distribution · sp_energy · ssen · neso
→
6. Policywhich LPA / local plan applies → agentic readingplanning_data → LLM

Try it: python scripts/site_report.py <lat> <lon> runs steps 1–5 (grid first, then NESO filtered by the grid supply points it found) and writes a map + every parsed response to one HTML page.

2. Sources

planning_data · planning.data.gov.uk

On the polygon = likely blocker or very special circumstances; nearby = setting / consultation. Absence is a finding too.

flood-risk-zone, flood-storage-areaUSEDSecond source for flood zone 2/3 (cross-checks ea_flood).

3. Gaps

  • Checks still run on the point, not the polygon. Steps 3 and 5 query “at the coordinate” or “within N km”. Next: intersect with the title polygon, and report two tiers: on site (can block) vs within X km (consultation / setting), each with a distance.
  • Grid data outside UKPN's area. ssen covers SSEN Transmission (north Scotland) only. nged covers the South West, South Wales and the Midlands; ssen_distribution central southern England and north Scotland; sp_energy covers central and southern Scotland (SPD) and Merseyside, North Wales, Cheshire (SPM). Still missing: Northern Powergrid, ENWL. Opendatasoft and CKAN portals reuse the shared opendatasoft / ckan modules, so each is a small file. Overhead lines: UKPN, SSEN Distribution, SSEN Transmission and SP Energy Networks have them; NGED publishes shapefiles only.
  • Transmission network. National Grid publishes lines, towers and substations as shapefiles (no API).
  • Nearby BESS precedent. DESNZ Renewable Energy Planning Database (quarterly CSV) lists battery projects with coordinates and planning outcome.
  • Policy text. We know which local plan applies, not what it says: that is the agentic step.
  • Terrain outside England. LIDAR is England only; Scotland / Wales fall back to the 90 m DEM (Scottish and Welsh LIDAR exist as separate downloads).

4. Removed

  • Overpass (OpenStreetMap power data): module, tests and fixtures deleted. The only responsive mirror was Russian-hosted (maps.mail.ru); the replacements timed out all day. UKPN's own data replaces it and is authoritative.
  • EA real-time flood monitoring (flood warnings, flood warning areas, monitoring stations): operational data, not a planning constraint. ea_flood now models only Flood Zones 2/3.
